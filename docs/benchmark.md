# 캐시 사용·미사용 성능 비교 (`cmd/cachebench`)

`cachebench`는 같은 상품 조회를 **캐시 없이 원본 API만 부르는 경우(OFF)** 와 **mini-Redis를 cache-aside로 거치는 경우(ON)** 로 나눠, 조건 조합 전체를 한 번에 돌리고 실행별 결과와 요약을 파일로 남기는 측정 도구입니다. 기존 코드는 고치지 않고 `cmd/cachebench/` 아래 새 파일로만 구성했습니다.

```text
캐시 OFF: cachebench ──GET──▶ 원본 모형
캐시 ON : cachebench ──GET──▶ mini-Redis
                         ├─ 200(HIT)  → 저장된 응답을 풀어 검증
                         └─ 404(MISS) → 원본 모형 GET → mini-Redis PUT(TTL) → 검증
```

## 1. 빠른 시작

모듈 루트(`go.mod`가 있는 폴더)에서 실행합니다. mini-Redis는 도구가 직접 빌드해서 띄우므로 따로 실행할 필요가 없습니다.

```bash
# 계획과 예상 소요 시간만 확인
go run ./cmd/cachebench -dry-run

# 동작 확인용 짧은 측정 (약 6분)
go run ./cmd/cachebench -quick

# 본 측정 (약 55분): 시나리오 4개 × 캐시 OFF/ON × AOF off/on × 원본 0/20ms × 동시 1/20 × 5회
go run ./cmd/cachebench -label "전원 연결, 다른 앱 종료"
```

결과는 `bench-results/<시각>-<무작위>/`에 `report.md`, `summary.csv`, `runs.csv`, `meta.json`, `server-aof-*.log`로 저장되고, 터미널에도 요약 표가 나옵니다. 측정 중 Ctrl+C를 누르면 끝난 실행까지만 집계해 저장합니다.

일부 조건만 돌리려면 목록 옵션을 줄이면 됩니다.

```bash
# 캐시 효과만 (약 35분)
go run ./cmd/cachebench -scenarios warm

# AOF 비용만: 지속 쓰기에서 AOF off/on 비교
go run ./cmd/cachebench -scenarios write -write-duration 30s -repeats 7

# 원본 지연을 더 다양하게 넣어 손익분기점 찾기
go run ./cmd/cachebench -scenarios warm -delays 0,1,5,20,50 -concurrency 20
```

### 주요 옵션

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `-scenarios` | `warm,cold,stampede,write` | 아래 "시나리오" 참고 |
| `-cache` | `off,on` | 비교할 캐시 모드 |
| `-aof` | `off,on` | mini-Redis AOF 설정 |
| `-delays` | `0,20` | 원본 모형의 인위적 지연(ms) |
| `-concurrency` | `1,20` | 동시 요청 수(닫힌 루프 워커 수) |
| `-repeats` | `5` | 조건별 반복. 반복마다 OFF·AOF off·AOF on의 실행 순서를 한 칸씩 돌립니다 |
| `-products` | `100` | 웜 캐시·지속 쓰기의 키 수(균등 분포) |
| `-value-bytes` | `1024` | 상품 응답 JSON 크기(바이트, 이하로 맞춤) |
| `-warmup` / `-duration` | `3s` / `30s` | 웜 캐시의 준비(집계 제외)·본 측정 시간 |
| `-write-duration` | `10s` | 지속 쓰기의 본 측정 시간. 이 초 수만큼 1초 주기 Sync를 포함합니다 |
| `-cold-keys` | `1000` | 빈 캐시에서 한 번씩 조회할 키 수 |
| `-stampede-keys` / `-stampede-requests-per-key` | `500` / `2` | 스탬피드의 키 수, 키당 연속 요청 수 |
| `-timeout` | `5s` | 조회 1건(캐시 흐름 전체)의 제한 시간 |
| `-auth` | `true` | 띄운 mini-Redis에 Bearer 인증을 켭니다(운영과 동일) |
| `-miniredis-bin` | 없음 | 직접 빌드한 서버 바이너리를 측정. 해시와 빌드 정보가 결과에 남습니다 |
| `-redis-url`, `-token` | 없음 | 이미 실행 중인 mini-Redis를 대상으로 측정. `-aof`에는 그 서버의 설정을 한 값으로 적습니다 |
| `-quick` | `false` | 준비 1초, 측정 5초, 쓰기 3초, 반복 2회, 키 수 축소 |
| `-label` | 없음 | 측정 환경 메모. 결과 파일에 함께 남습니다 |

## 2. 동작 방식

### 측정 대상과 원본 모형

- **mini-Redis**: 도구가 `go build ./cmd/miniredis`로 빌드하고, **캐시 ON 실행마다 프로세스를 새로 띄웁니다.** 루프백의 빈 포트, 빈 임시 AOF 파일, `MINI_REDIS_DEBUG=false`, 무작위 Bearer 토큰을 쓰고 사용자의 `MINI_REDIS_*` 환경 변수는 넘기지 않습니다. 실행이 끝나면 SIGINT로 정상 종료시키고 임시 AOF를 지웁니다. 그래서 어떤 실행도 앞선 실행의 키, AOF 크기, 밀린 Sync·재작성 작업을 물려받지 않습니다. 사용자의 `data/appendonly.aof`는 건드리지 않습니다. (`-redis-url`로 외부 서버를 쓰면 이 보장이 없습니다. 서버 하나를 계속 쓰고, 실행마다 다른 키 접두사를 쓴 뒤 그 키만 지웁니다.)
- **원본 모형**: 도구 안에 있는 HTTP 서버입니다. 상품 응답을 시작 시 미리 만들어 두고 이후 바꾸지 않으므로 **잠금이 전혀 없습니다.** 호출 수만 원자적으로 세고 `time.Sleep`으로 지연한 뒤 응답합니다. 기존 `internal/demo/demo_test.go`의 원본 모형은 요청 전체에 잠금을 잡아서 지연을 넣으면 모든 요청이 한 줄로 처리되고 캐시 효과가 과장되는데, 이 모형에서는 동시 요청이 겹쳐 처리됩니다(`TestOriginDoesNotSerialiseDelay`로 검증).

### 시간을 재는 구간

조회 1건의 시간은 **요청을 시작한 순간부터 최종 상품 응답을 끝까지 읽고 검증한 순간까지**입니다. ON에서는 캐시 조회, 저장값 JSON 해제, 미스 시 원본 조회와 캐시 저장(PUT)까지 모두 포함됩니다. 검증은 양쪽 모두 상품 JSON을 풀어 ID·이름·가격·버전·설명 전체를 기대값과 비교하므로 같은 비용이 듭니다.

- **연결**: 실행마다 HTTP 클라이언트를 새로 만들어 모든 실행이 연결 0개에서 시작합니다. 측정 전에 서버마다 동시 수의 2배만큼 요청을 보내되 응답 본문을 전부 받을 때까지 닫지 않아, 연결이 그 수만큼 따로 만들어지도록 강제합니다(Go의 HTTP 클라이언트는 응답을 다 읽은 연결을 조금 늦게 반납하므로 워커 수만큼의 여분이 필요합니다). 다만 본문이 없는 응답은 연결이 일찍 반납될 수 있어 이 준비만으로 연결 수가 보장되지는 않습니다. 그래서 **측정 구간 안에서 새 연결을 열려고 시도한 횟수**(`DialContext` 호출 수)를 세어 `dial_attempts_in_window`에 남기고, 0이 아니면 경고합니다. 연결이 준비됐다는 근거는 준비 단계가 아니라 이 값입니다. 응답 본문은 끝까지 읽고 닫으며, 프록시와 압축은 끕니다.
- **지연 기록**: 고정 크기 히스토그램(2의 거듭제곱 구간마다 128칸)에 기록합니다. 기록은 배열 한 칸을 올리는 것이라 **지연 표본을 기록하느라 메모리를 할당하지는 않습니다.** HTTP 요청과 JSON 처리의 할당은 그대로 있으므로 측정기의 GC가 없어지는 것은 아니며, GC 횟수와 정지 시간은 따로 기록합니다. 백분위수의 상대 오차는 0.4% 이하이고, 건수·평균·최소·최대는 정확합니다. 히스토그램은 합칠 수 있어서 반복들을 합친 백분위수도 같은 방식으로 구합니다.
- **실패는 빠른 응답으로 세지 않습니다.** 오류(연결 실패, 예상 밖 상태 코드), 타임아웃, 검증 실패(값 불일치)를 따로 세고 지연·처리량 집계에서 뺍니다. 캐시 조회가 실패하면 원본으로 우회하지 않고 오류로 셉니다. 우회하면 캐시 장애가 정상 응답 속에 숨기 때문입니다.
- 원본에서 받은 값을 캐시에 저장(PUT)하는 데만 실패하면 사용자 응답은 성공이므로 성공으로 세고, `cache_set_failures`에 따로 기록합니다.

### 시나리오

| 시나리오 | 끝나는 기준 | 무엇을 보나 |
|---|---|---|
| `warm` 웜 캐시 | 시간 | 캐시 적중 시의 이득, 원본 호출 감소 |
| `cold` 빈 캐시 | 요청 수 | 첫 조회(미스) 1건의 비용 |
| `stampede` 스탬피드 | 요청 수 | 같은 키에 동시 미스가 몰릴 때의 원본 호출 수 |
| `write` 지속 쓰기 | 시간 | AOF off 대비 AOF on의 쓰기 비용 |

**웜 캐시(`warm`)**

1. ON은 상품 100개를 한 번씩 조회해 채웁니다. **모든 조회가 "미스 → 원본 → 저장 성공"이어야 하고, 이어서 모든 키를 순수 GET으로 다시 읽어 실제로 저장됐는지 확인합니다. 하나라도 어긋나면 그 실행을 무효로 표시하고 측정하지 않습니다**(`valid=false`, 요약에서 제외, 경고).
2. 워커 수만큼 고루틴이 균등 분포로 상품을 골라 쉬지 않고 조회합니다(닫힌 루프).
3. 준비 시간 동안 시작한 요청은 실행만 하고 기록하지 않습니다. 본 측정 시간 동안 **시작한** 요청만 집계합니다.
4. 정상이라면 ON의 원본 호출은 0, 적중률은 100%입니다.

**빈 캐시(`cold`)**: 새 서버에서 서로 다른 키 1,000개를 한 번씩 조회합니다. ON에서는 모든 요청이 첫 조회라 전부 미스입니다. 시간이 아니라 요청을 다 처리하면 끝납니다(시간으로 끝내면 금방 캐시가 채워져 웜 측정이 됩니다). 핵심 수치는 `미스 추가 비용`(ON의 미스 p50 − OFF의 p50)입니다.

**스탬피드(`stampede`)**: 키 500개를 **키당 2번씩 연속으로** 배치합니다(`k0,k0,k1,k1,…`). 동시 1에서는 첫 번째가 미스, 두 번째가 적중입니다. 동시 20에서는 같은 키의 두 요청이 동시에 나가 둘 다 미스가 나고 원본을 두 번 부릅니다. mini-Redis에는 동시 미스를 합치는 기능이 없어서 이 현상이 그대로 드러나며, 키당 원본 호출 수(평균·최대)와 `keys_multi_origin`으로 기록합니다. 적중과 미스가 섞이므로 전체 p50 대신 `hit_p50_ms`와 `miss_p50_ms`를 보세요.

**지속 쓰기(`write`)**: 키 100개에 PUT만 계속 보냅니다(덮어쓰기라 메모리는 늘지 않습니다). 원본과 캐시 OFF는 관여하지 않고 **AOF off와 AOF on을 비교**합니다. 측정이 10초 이어지므로 1초 주기 Sync를 여러 번 포함하고, AOF가 커지면 재작성도 측정 구간 안에서 일어납니다. 끝나면 **PUT이 한 번이라도 성공한 키를 전부 다시 읽어 검증합니다.** 이 검증은 원본 우회나 재저장이 없는 순수 GET이라서, 서버가 200으로 답하고 실제로는 저장하지 않았다면 값이 없는 것으로 드러납니다. 값이 없거나 다르면, 또는 성공한 PUT이 하나도 없으면 그 실행을 무효로 합니다. 캐시 ON/OFF 비교가 아니라 AOF 비용을 보기 위한 시나리오입니다.

AOF on 실행에서는 도구가 AOF 파일을 밖에서 50ms 간격으로 관찰해 다음을 남깁니다.

- `aof_est_sync_periods`: 측정 구간의 초 수(내림). **Sync가 실제로 실행·완료된 횟수가 아닙니다.** 서버가 Sync 횟수를 알려 주지 않아서, "1초 주기라면 이만큼 들어갔을 것"이라는 추정으로만 쓰세요.
- `aof_rewrites_seen`: 파일이 교체되거나 줄어든 횟수(재작성으로 판단).
- `aof_bytes_start` / `aof_bytes_end` / `aof_bytes_max`: 구간 시작·끝·최대 파일 크기.

### 반복, 순서, 비교 방법

같은 (시나리오, 원본 지연, 동시 수)에서 한 반복은 **OFF, ON(AOF off), ON(AOF on)을 연달아** 측정합니다. 반복마다 이 순서를 한 칸씩 돌려서(1회차 OFF→off→on, 2회차 off→on→OFF, …) 시간에 따른 기기 상태 변화가 한 쪽에 쏠리지 않게 합니다.

비교 배수는 **같은 반복 안의 실행끼리 짝지어** 구합니다. 예를 들어 `처리량 배수`는 반복마다 `ON 처리량 ÷ 같은 반복의 OFF 처리량`을 구한 뒤 그 중앙값이고, 최소–최대도 함께 냅니다. 짝지은 두 실행은 길어야 몇 분 간격이라, 멀리 떨어진 시점의 중앙값끼리 나누는 것보다 시간에 따른 편향이 작습니다. AOF 비용(`aof_rps_ratio_on_vs_off`, `aof_p50_delta_ms`, `aof_p99_delta_ms`)도 같은 반복의 AOF off 실행과 짝지어 구합니다.

### 자원 사용량

- **측정기**: 측정 구간 동안 측정기 프로세스(원본 모형 포함)가 쓴 CPU 시간(`bench_cpu_s`), 초당 코어 수(`bench_cpu_cores`), GC 횟수와 정지 시간(`bench_gc_count`, `bench_gc_pause_ms`).
- **서버**: 띄운 mini-Redis가 종료할 때까지 쓴 CPU 시간(`server_cpu_s`)과 최대 메모리(`server_max_rss_mb`), 종료 상태(`server_exit`). 실행마다 새 프로세스라 시작·미리 채우기·측정·정리가 모두 포함됩니다.

측정기가 전체 코어의 절반 넘게 쓰는 조건은 자동으로 경고합니다. 그 조건의 처리량은 서버가 아니라 측정기와 CPU 경합이 한계일 수 있습니다.

## 3. 결과 읽는 법

### 순서

1. **`report.md`의 "자동 점검"부터 봅니다.** 무효 실행, 실패가 있는 조건, 측정 구간에 새 연결이 생긴 조건, 서버 비정상 종료, 반복 간 처리량 편차가 큰 조건, 측정기가 CPU를 많이 쓴 조건, AOF Sync 주기를 포함하지 못한 조건, p99 표본이 적은 조건이 나옵니다. 여기 걸린 조건의 숫자는 그대로 인용하지 마세요.
2. **측정 자체가 맞는지 이론값으로 확인합니다.** 원본 20ms, 캐시 OFF의 처리량은 동시 수 × 1000/20을 넘을 수 없습니다(동시 1이면 약 50, 동시 20이면 약 1,000 req/s). OFF의 p50은 20ms보다 조금 커야 합니다.
3. **0ms 조건으로 캐시 자체의 비용을 봅니다.** 웜 캐시에서 ON과 OFF는 둘 다 HTTP 왕복 한 번이라 비슷하거나 ON이 약간 느린 것이 정상입니다. 이미 빠른 원본 앞에서는 인증 검사와 저장값 해석 비용이 더 크기 때문입니다.
4. **20ms 조건으로 캐시의 이득을 봅니다.** 웜 캐시의 `p50 개선`, `처리량 배수`, `원본 호출 감소`가 핵심 수치입니다. 다만 이 배수는 **인위적인 20ms 대기를 건너뛴 효과**이지 "mini-Redis가 원본보다 100배 빠르다"는 뜻이 아닙니다. 원본 지연을 여러 값으로 돌리면(`-delays 0,1,5,20,50`) 어느 원본 비용부터 캐시가 유리해지는지 찾을 수 있습니다.
5. **빈 캐시로 첫 조회 비용을, 스탬피드로 원본 쏠림을 봅니다.** 빈 캐시의 `미스 추가 비용`이 미스 1건이 OFF보다 더 드는 시간이고, 스탬피드 동시 20의 `키당 원본 호출`이 1보다 크면 그만큼 원본에 요청이 몰렸다는 뜻입니다. 스탬피드에서 적중률이 0%에 가까운 것은 고장이 아니라 동시 미스를 일부러 유도한 결과입니다.
6. **AOF 비용은 지속 쓰기 표에서 봅니다.** `AOF on÷off 처리량`이 1보다 작은 만큼, `AOF p50 증가`만큼이 비용입니다. 이 값은 기록 덧붙이기, 동기화, 재작성이 합쳐진 **"AOF가 켜진 상태에서 관측한 비용"** 이고 항목별로 나눌 수 없습니다. `추정 Sync 주기`와 `관측된 재작성`으로 그 구간에 무슨 일이 있었는지 확인하세요.

### AOF 수치의 뜻

- 웜 캐시는 거의 GET만 하므로 AOF off/on 차이가 나와도 AOF 비용이 아닙니다.
- 빈 캐시·스탬피드는 측정 구간이 1초보다 짧을 수 있어(표의 `측정 시간`) Sync를 한 번도 포함하지 못할 수 있습니다. 이 행들의 AOF 차이는 **"그 순간 AOF가 켜진 상태에서 관측한 비용"** 으로만 읽으세요.
- 지속 쓰기의 지연도 **"PUT 응답이 돌아올 때까지"** 입니다. mini-Redis는 기록을 파일에 덧붙인 뒤 응답하고 디스크 동기화(fsync)는 1초 주기로 따로 하므로, "동기화가 끝날 때까지의 지연"은 이 도구로 재지 않습니다. 동기화와 재작성의 영향은 개별 PUT의 p50이 아니라 p99 같은 꼬리 지연과 처리량으로 나타납니다.

### 숫자를 고르는 기준

- **처리량**: `success_rps_median`과 최소–최대 범위를 함께 봅니다. 범위가 겹치면 차이가 있다고 단정하지 마세요. 측정 시간이 1초보다 짧은 빈 캐시·스탬피드의 처리량은 참고만 하세요.
- **지연**: 일반적인 경우는 `p50_ms_median`, 꼬리는 `p99_ms_pooled`를 우선 봅니다. 동시 1·원본 20ms·30초면 표본이 약 1,500개라 반복별 p99는 상위 15개 정도로 정해집니다.
- **비교 열**은 같은 반복끼리 짝지은 값이며, `paired_repeats_*`가 짝지어진 반복 수입니다.

### 발표·문서에 옮길 때 함께 적을 것

- 측정 기기(`cpu`, `os_arch`), `source_hash`, 서버 바이너리 해시, 조건(키 수, 응답 크기, 반복 수)
- "같은 기기 루프백, 원본 지연은 인위적 sleep, 균등 분포 100개 키 = 적중률 100% 최선의 경우"라는 전제
- 실패 건수와 무효 실행 수(0이어야 비교 가능)

## 4. 출력 파일과 열

`runs.csv`는 실행 하나가 한 줄, `summary.csv`는 조건 하나가 한 줄입니다. 두 파일 모두 끝에 `commit, source_hash, go_version, os_arch, cpu, num_cpu, server_mode, server_bin_sha256, server_go_version, server_config` 열이 붙습니다.

| 열 (`runs.csv`) | 의미 |
|---|---|
| `scenario`, `cache`, `aof`, `origin_delay_ms`, `concurrency`, `repeat`, `order` | 조건. `order`는 그 반복 안에서 몇 번째로 실행했는지 |
| `valid`, `invalid_reason` | 무효 실행 여부와 사유(예: 미리 채우기 실패) |
| `keys`, `requests`, `successes`, `elapsed_s`, `success_rps` | 측정 구간 요청 수, 성공 수, 측정 시간, 초당 성공 응답 |
| `mean_ms`, `p50_ms`, `p95_ms`, `p99_ms`, `max_ms` | 성공 요청의 지연 분포에서 구한 통계(가장 가까운 순위 방식) |
| `hit_p50_ms`, `miss_p50_ms` | 적중·미스 요청만의 p50 |
| `p99_tail_samples` | p99 이상에 있는 표본 수. 10 미만이면 p99가 불안정 |
| `errors`, `timeouts`, `validation_failures`, `cache_set_failures` | 실패 분류. 앞의 셋은 집계에서 제외 |
| `hits`, `misses`, `hit_ratio` | 캐시 GET 200·404 수와 적중률(ON만) |
| `origin_calls`, `origin_calls_per_request`, `origin_calls_per_key`, `origin_calls_key_max`, `keys_multi_origin` | 측정 구간의 원본 호출 수, 요청당, 원본을 부른 키당 평균·최대, 2번 이상 부른 키 수 |
| `prefill_failures`, `cleanup_failures`, `dial_attempts_in_window` | 미리 채우기 실패 수, 정리 실패 수, 측정 구간의 새 연결 시도 수 |
| `bench_cpu_s`, `bench_cpu_cores`, `bench_gc_count`, `bench_gc_pause_ms` | 측정 구간 동안의 측정기 자원 사용 |
| `server_cpu_s`, `server_max_rss_mb`, `server_exit` | 띄운 서버의 전체 수명 CPU·최대 메모리·종료 상태(`ok`, `killed`, 오류) |
| `aof_est_sync_periods`, `aof_bytes_start`, `aof_bytes_end`, `aof_bytes_max`, `aof_rewrites_seen` | AOF on 실행에서 관찰한 값 |
| `error_samples` | 실패 메시지 예시 |

`summary.csv`에는 유효한 반복들의 중앙값(`*_median`), 처리량 최소·최대와 편차(`rps_spread_pct`), 합산 백분위수(`*_pooled`), 실패 합계(`*_total`), 무효 실행 수(`invalid_runs`), OFF 대비 짝 비교(`speedup_p50_vs_off`, `speedup_p99_vs_off`, `rps_ratio_vs_off`와 최소·최대, `origin_call_reduction_pct`, `miss_extra_ms_vs_off`), AOF off 대비 짝 비교(`aof_rps_ratio_on_vs_off`와 최소·최대, `aof_p50_delta_ms`, `aof_p99_delta_ms`, `aof_miss_p50_delta_ms`)가 들어갑니다.

`meta.json`에는 환경과 조건 전체, 그리고 측정한 서버 바이너리의 SHA-256, Go 버전, 빌드 설정(`-race`, CGO, vcs 정보 등)이 들어갑니다.

## 5. 재현성 정보가 증명하는 범위

| 실행 방식 | 증명되는 것 | 증명되지 않는 것 |
|---|---|---|
| 기본(도구가 빌드) | `source_hash`의 소스로 빌드한 바이너리의 해시·Go 버전·빌드 설정, 디버그 OFF·인증·빈 AOF로 띄웠다는 것 | 없음 |
| `-miniredis-bin` | 그 바이너리의 해시·Go 버전·빌드 설정, 도구가 지정한 실행 설정 | 그 바이너리가 어떤 소스에서 나왔는지(`source_hash`는 그 바이너리를 설명하지 않음) |
| `-redis-url` | AOF 모드(`/health`와 `-aof` 선언이 다르면 실행을 거부) | 서버 코드, 빌드, 디버그 설정, 서버 위치. 결과에 **사용자 선언값**으로 표시됩니다. 서버 CPU·메모리와 AOF 관찰값도 없습니다 |

커밋 해시는 작업 트리에 변경이 있으면 `-dirty`가 붙습니다. 커밋되지 않은 코드를 측정했다면 `source_hash`가 같은 결과끼리만 비교하세요.

## 6. 한계

- **같은 기기·루프백 측정입니다.** CLI, 원본 모형(CLI 프로세스 안), mini-Redis가 CPU를 나눠 씁니다. 실제 배포에서는 캐시 왕복에 네트워크 지연이 더해져 ON의 이득은 줄고 0ms 조건의 손해는 커집니다.
- **측정기도 부하입니다.** 동시 20·0ms에서는 측정기가 여러 코어를 쓰므로 처리량은 "이 기기에서 측정기와 서버가 CPU를 나눠 쓸 때의 처리량"입니다. 서버의 최대 처리량을 재려면 측정기를 다른 기기에 두어야 합니다.
- **원본 지연은 `time.Sleep`입니다.** 실제 DB처럼 부하가 늘면 느려지는 성질이 없습니다.
- **닫힌 루프 측정입니다.** 동시 수를 고정하므로 처리량은 "이 동시성에서 얻은 처리량"이며, 정해진 요청률을 견디는지 보는 시험이 아닙니다. 서버가 느려지면 요청도 덜 보내므로 꼬리 지연이 실제보다 작게 보일 수 있습니다.
- **균등 분포·키 100개 웜 캐시는 최선의 경우입니다.** 키 수를 늘리거나 인기 편중·TTL 만료·무효화가 섞이면 적중률이 떨어집니다. TTL 만료·무효화 혼합 시나리오는 아직 없습니다.
- **Sync는 세지 못하고, 재작성은 밖에서 관찰합니다.** `aof_est_sync_periods`는 측정 구간의 초 수일 뿐 완료된 Sync 횟수가 아닙니다. 재작성은 50ms 간격으로 파일을 관찰해 세므로 그 사이에 두 번 일어나면 한 번으로 셉니다.
- **지속 쓰기는 덮어쓰기입니다.** 키가 계속 늘어나는 쓰기나 삭제가 섞인 쓰기의 AOF 비용은 다를 수 있습니다.

## 팀 PRD T4 기본 프로필로 측정하기

팀 PRD의 기본 프로필(원본 100ms, 사용자 20, 워밍업 10초, 측정 30초, 3회, 영속성 비활성)은 다음 명령입니다. 약 4분 걸립니다.

```bash
go run ./cmd/cachebench -scenarios warm -delays 100 -concurrency 20 \
  -warmup 10s -duration 30s -repeats 3 -aof off -products 100
```

이 프로필의 결과와 해석은 [docs/results/prd-t4.md](results/prd-t4.md)에 정리합니다. 기기를 바꿔 다시 측정했다면 `bench-results/<실행 ID>/`의 파일로 그 문서와 `docs/results/` 아래 원자료를 갱신하세요.
