# 설계 선택과 이유

[팀 PRD](learning/PRD.md) 4장·5장의 "내 선택·이유·보장 범위·한계"를 한곳에 정리한 문서입니다. 자세한 동작은 [구조와 설계](architecture.md), [AOF 영속성과 복구](persistence.md)에 있습니다.

## 핵심 설계 결정 (PRD 4장)

| 결정 | 내 선택 | 이유 | 보장 범위 | 한계 |
|---|---|---|---|---|
| 해시 함수 | FNV-1a 64비트 직접 구현 (`hashtable.Hash`). 서버는 프로세스마다 무작위 시드로 시작 상태를 바꾸고 마지막에 64비트 혼합 단계를 거침(`NewSeeded`) | XOR 후 소수 곱셈 두 연산뿐이라 원리를 한 줄씩 설명할 수 있고, 공개된 기준 벡터로 구현을 검증할 수 있음. 시드는 미리 계산한 충돌 키가 다른 프로세스에서는 통하지 않게 함 | 시드 없는 `Hash`는 기준 벡터와 일치(`TestHashFNV1aKnownVectors`). 시드가 다르면 배치가 달라지고, 시드 없이 한 버킷에 몰리던 키가 흩어짐(`TestSeededTableSpreadsKeysThatCollideUnseeded`) | 암호학적 키 해시(SipHash 등)가 아니므로 의도적 충돌을 어렵게 할 뿐 불가능하게 보장하지는 않음. 해시는 파일에 저장하지 않으므로 재시작마다 시드가 바뀌어도 무방 |
| 충돌 처리 | 체이닝(연결 리스트). 노드에 해시값을 함께 저장 | 삭제가 단순하고 충돌을 관찰하기 쉬움. 해시를 먼저 비교해 문자열 비교를 줄임 | 충돌 키의 첫·중간·끝 삭제, 갱신, 재삽입에서 다른 키 보존(`TestTableCollisionDeletePositions`) | 한 버킷에 몰리면 저장·조회·삭제가 O(n). 체인이 64 이상으로 길어지면 `LONG_CHAIN` 경고를 남겨 알 수 있게 함(키 이름은 기록하지 않음) |
| 용량·재해싱 | 16버킷에서 시작, 새 키 삽입으로 적재율 0.75를 넘으면 2배로 일괄 확장 | 값·TTL 보존을 한 번에 검증하기 쉬움 | 확장 전후 키 수·값·만료 시각 보존(`TestTableResizeThresholdAndPreservation`) | 확장·축소하는 동안 모든 요청이 대기. 축소는 만료 정리가 한 바퀴를 마쳤을 때 사용 버킷이 1/8 미만이면 절반씩 줄이며(최소 16), 삭제 직후 즉시 줄이지는 않음(`TestShrinkAfterMassDeletion`, `TestBucketArrayShrinksAfterExpiredBurst`) |
| 데이터 용량 | 키+값+항목당 64바이트의 근사 상한(기본 256 MiB). 넘는 증가분은 503으로 거부 | 메모리가 무한히 늘지 않게 하면서 기존 데이터는 지킴 | 거부 시 기존 값·TTL·AOF 불변. 같은 크기·더 작은 갱신과 삭제는 허용 | 프로세스 메모리 상한이 아님. 버킷 배열·런타임은 별도. 자동 축출(LRU 등) 없음 |
| 동시성 | 전역 Mutex 하나(`mu`)로 모든 테이블 접근 보호 + 변경 순서 게이트(`writeMu`) | 조회도 만료 노드를 지우는 쓰기라서 읽기 락으로 나누면 재확인 로직이 필요. 락 하나가 연산 순서를 가장 단순하게 보장 | 단일 키 연산은 순차 실행으로 설명 가능. 값·TTL 부분 갱신 없음. 레이스 탐지기 통과 | 읽기도 서로 기다림. 코어를 늘려도 저장소 연산은 병렬화되지 않음 |
| 만료 | 지연 만료 + 약 100ms 주기의 능동 정리 | 지연 만료로 정확성을 확보하고, 조회되지 않는 만료 키의 메모리는 주기 정리로 회수 | `now >= 만료 시각`이면 부재. 조회로 연장 없음. 과거 정리 작업이 새 값을 지우지 않음 | 물리 회수 시점은 부하와 키 수에 따라 늦어질 수 있음 |
| 시간원 | 실행 중에는 Go의 단조 시계 정보를 가진 시각, 파일에는 벽시계 절대 시각. 테스트는 `Clock` 인터페이스로 가짜 시계 주입 | 실행 중 벽시계가 바뀌어도 TTL이 흔들리지 않고, 재시작 후에도 남은 수명을 계산할 수 있음 | 밀리초 단위 TTL, 남은 TTL은 올림 | 재시작 사이에 벽시계가 틀어지면 TTL이 그만큼 달라짐 |
| 무효화 | 키별 `DELETE`. TTL은 보완 수단 | 사용자가 원하는 시점에 정확히 지울 수 있음 | 삭제 완료 후 시작한 조회는 새 저장이 없는 한 404 | 원본 조회 도중 무효화된 뒤 예전 값이 다시 저장되는 경합은 해결하지 않음 |

### 주요 함수의 시간 복잡도

| 함수 | 평균 | 최악 | 설명 |
|---|---|---|---|
| `Table.Get` / `Swap`(`Put`) / `Take`(`Delete`) | O(1) | O(n) | 버킷 하나의 체인을 한 번만 탐색. 모든 키가 한 버킷에 몰리면 O(n) |
| `Table.resize` (확장·축소) | O(B + n) | O(B + n) | B는 기존 버킷 수, n은 키 수. 기존 버킷을 모두 훑으며 노드를 새 배열로 옮김. 확장할 때는 B와 n이 비례하므로 O(n)이고 삽입 n번에 걸쳐 나누면 삽입당 평균 O(1). 대량 삭제 뒤 축소할 때는 B가 n보다 훨씬 클 수 있어 버킷 수가 비용을 좌우함 |
| `Store.Set` / `Get` / `Delete` | O(1) | O(n) | 테이블 연산에 검증과 락이 더해짐. SET은 용량 확인과 저장으로 체인을 두 번, 삭제는 한 번 탐색. AOF 사용 시 SET·DELETE에 파일 쓰기 1회 추가 |
| 능동 만료 정리 (`Table.Reap`) | 전체 한 바퀴 O(버킷 수 + n) | 전체 한 바퀴 O(n²) | 한 번에 256 탐색 단위(빈 버킷 확인 + 노드 방문)씩 락을 나눠 잡음. 노드는 커서가 기억한 앞 노드로 바로 떼어 내므로 긴 체인에서도 보통 노드당 O(1). 다만 배치 사이에 그 앞 노드가 삭제됐거나 버킷 머리에 새 노드가 들어온 경우에는 체인을 다시 훑어 찾으므로, 그런 일이 매번 일어나는 최악의 경우 한 체인에서 O(길이²)까지 가능. 256 탐색 단위는 방문 횟수의 상한이지 비교 횟수나 실행 시간의 엄격한 상한이 아님 |

## 영속성 (PRD 5장)

| 방식 | 비교 | 내 선택 |
|---|---|---|
| 스냅샷(RDB 방식) | 복구가 단순하지만 마지막 저장 이후의 변경을 모두 잃음 | 선택하지 않음. 다만 AOF 재작성이 유효 항목만 새 파일로 쓰는 스냅샷 역할을 함 |
| 추가 전용 로그(AOF) | 변경마다 기록하므로 손실 구간이 짧음. 로그가 커지고 재생 시간이 듦 | **선택.** 손실 구간을 약 1초로 줄일 수 있고 "기록 → 메모리 반영" 순서를 설명하기 쉬움 |

| 항목 | 결정 |
|---|---|
| 대상 장애 | 프로세스 종료·강제 종료 후 재시작. 전원·저장 장치 장애는 검증 범위가 아님 |
| 복구 지점·허용 손실 | 마지막 디스크 Sync까지. Sync는 기본 약 1초 주기(`MINI_REDIS_AOF_SYNC_INTERVAL_MS`로 조정)이며 주기는 목표이지 손실 상한이 아님 |
| 성공 응답과 디스크 반영 순서 | 파일 쓰기 → 메모리 반영 → 200 응답. 디스크 Sync는 그 뒤 백그라운드에서 수행 |
| 저장 실패 시 | 쓰기·Sync 실패 후에는 변경을 503으로 거부하고 조회는 유지. 성공으로 표시하지 않음 |
| 복구 실패 시 | 잘린 마지막 기록은 잘라내고 기동. 중간 체크섬 손상은 기동을 거부하고 `aofrepair`로 사람이 판단 |
| TTL 기록 | 절대 만료 시각(벽시계). 재시작 시 남은 수명만 복원하고 이미 지난 키는 버림 |
| 재생 | 시작할 때 파일을 1 MiB 버퍼로 순차 읽기. 요청을 받기 전에 끝냄 |
| 파일 크기 | 유효 항목만 다시 쓰는 재작성으로 줄임. 임시 파일 → Sync → rename → 디렉터리 Sync |
| 파일 상한 | 따로 지정하지 않으면 데이터 상한의 2배(최소 256 MiB). 아래 참고 |

### AOF 상한을 데이터 상한의 2배로 둔 이유

같은 키 하나가 메모리 계산과 AOF에서 차지하는 양이 다릅니다. AOF는 값을 Base64로 적어 약 1.33배가 되고, 프레임·JSON 필드·만료 시각, 그리고 나중에 그 키를 지울 수 있도록 미리 잡아 두는 삭제 예약이 더해집니다.

두 상한을 같게(4 MiB) 두고 채워 본 결과, 데이터 상한에 도달하기 전에 AOF 상한이 먼저 걸렸습니다.

| 값 크기 | 쓰기가 거부된 시점의 데이터 사용량 | 받은 오류 |
|---|---|---|
| 10바이트 | 데이터 상한의 53% | `PERSISTENCE_UNAVAILABLE` |
| 1 KiB | 72% | `PERSISTENCE_UNAVAILABLE` |
| 64 KiB | 74% | `PERSISTENCE_UNAVAILABLE` |

AOF 상한을 2배로 둔 같은 시험 조건(짧은 ASCII 키, 값 0바이트~64 KiB, TTL 유무, 키마다 한 번 저장)에서는 AOF보다 데이터 용량 제한이 먼저 적용되어 `CAPACITY_EXCEEDED`로 거부됐습니다. 이때 AOF 점유는 상한의 56~94%였습니다(TTL이 있는 작은 값이 가장 높음). 마지막 레코드가 들어갈 자리가 모자라면 거부되므로 데이터 사용량이 정확히 100%가 되는 것은 아닙니다. `TestAOFHeadroomLetsDataLimitBindFirst`가 이 시험 조건의 관계를 고정합니다.

2배는 일반적인 상품 키·값 조건에서 여유를 확보하기 위한 기본 정책이며, 모든 입력과 누적 기록에서 데이터 상한 도달을 보장하지는 않습니다.

- `<`, `>`, `&`가 많이 들어간 키는 JSON에서 문자당 6바이트로 늘어나고 삭제 예약에도 같은 길이가 잡히므로 2배로 부족할 수 있습니다.
- 같은 키를 반복해 덮어쓰면 재작성 전까지 예전 기록이 파일에 남아 일시적으로 상한에 닿을 수 있습니다. 이때는 재작성이 공간을 되찾습니다.
- GET의 지연 삭제는 삭제 예약을 바로 줄이지 않아 재작성 전까지 예약이 보수적으로 남습니다.

`MINI_REDIS_AOF_MAX_BYTES`를 직접 지정하면 그 값을 그대로 쓰며, 데이터 상한의 2배보다 작으면 시작할 때 `AOF_LIMIT_BELOW_DATA_LIMIT` 경고를 남깁니다.
