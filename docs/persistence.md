# AOF 영속성과 복구

## 보장과 실패

기본 활성화이며 파일은 프로젝트 전용 `MINIAOF1` 형식입니다. 변경은 길이·길이 CRC·JSON·본문 CRC 프레임으로 append합니다. 값은 Base64로 보존하고 TTL은 절대 만료 시각으로 기록합니다. Redis AOF와 호환되지 않습니다. Base64는 암호화가 아닙니다.

성공 응답은 파일 쓰기 후 메모리 반영까지 완료했다는 뜻입니다. 디스크 Sync 완료는 아니며 백그라운드가 약 1초마다 Sync합니다. 장애 시 마지막 동기화 이후 기록을 잃을 수 있습니다. 1초는 목표 주기이며 손실 상한이 아닙니다. 정상 종료는 마지막 Sync를 시도하고 서버의 종료 대기는 전체 5초입니다. 디스크 자체가 멈추면 종료도 완료하지 못할 수 있습니다.

기록·Sync 실패는 이후 변경을 거부하고 조회는 유지합니다. 미동기화 기록이 3초 넘게 밀려도 변경을 거부합니다. 별도로 변경 호출자의 결과 대기는 기본 3초입니다. 실행 전 거부는 나중에 실행하지 않지만 실행 중 디스크 호출은 강제로 취소할 수 없습니다. 이때 `PERSISTENCE_OUTCOME_UNKNOWN` 또는 연결 오류 뒤에 작업이 완료될 수 있습니다. 복구된 Sync 지연은 재개될 수 있지만 기록·Sync fatal 오류나 panic은 원인 점검 후 재시작이 필요합니다.

## 재시작·재작성·한도

시작 전에 기록을 재생합니다. 만료된 덮어쓰기도 이전 값을 지워 부활을 막습니다. 중단 중 흐른 시간도 TTL에 반영하며 시스템 벽시계가 틀리면 TTL이 달라질 수 있습니다. Linux·macOS 로컬 파일 시스템에서 단일 프로세스가 OS 파일 잠금을 사용합니다. NFS 등 네트워크 파일 시스템과 Windows AOF는 지원하지 않습니다.

자동 재작성은 유효 스냅샷과 동시 변경분으로 새 파일을 만들고 Sync 후 같은 디렉터리 rename·디렉터리 Sync로 교체합니다. 교체 전 실패하면 기존 파일을 유지합니다. 교체 후 디렉터리 Sync 실패는 장애로 보고 변경을 거부합니다. 스냅샷은 128 탐색 단위로 메모리 잠금을 나누지만 전체 순회·복사와 변경 대기는 남습니다. 변경분 버퍼 상한 8 MiB를 넘으면 재작성을 중단합니다.

기본 파일+삭제 예약량 상한은 256 MiB, 최소 재작성 기준은 4 MiB입니다. 마지막 기준의 두 배 성장, 충분한 성장과 예약 포함 점유율 75% 이상, 또는 실제 용량 거부가 재작성 계기가 됩니다. 75%만으로 DELETE마다 재작성하지 않습니다. 실패·공간 회수 없음은 1~60초 지연으로 재시도합니다. 실제 append 용량 거부 뒤 삭제는 정리를 앞당길 수 있습니다.

SET은 현재 키를 나중에 지울 DEL 공간도 예약합니다. 파일 한도 소진 뒤에도 이 공간으로 기존 키를 지울 수 있지만 물리 디스크 여유를 선할당하지는 않습니다. OS 용량 부족·장치 오류 시 삭제도 실패할 수 있습니다. 만료 정리는 DEL 기록을 남기지 않고 예약을 회수합니다. 지연 GET 삭제 뒤에는 보수적 예약이 남을 수 있으며 재작성에서 회수합니다.

## 백업·검사·복구

권장 백업은 서버를 정상 종료한 뒤 AOF 파일을 복사하는 것입니다. 실행 중 복사는 재작성·교체·꼬리 기록과 경합하므로 일관된 백업을 보장하지 않습니다. 원본과 별도의 안전한 보관 위치를 사용하세요.

```bash
# 서버를 멈춘 상태에서 실행
./bin/aofrepair -input data/appendonly.aof
# 보고서의 valid_bytes 이후를 버려도 되는 경우에만 새 파일로 복구
./bin/aofrepair -input data/appendonly.aof -output data/recovered.aof -allow-data-loss
MINI_REDIS_AOF_PATH=data/recovered.aof ./bin/miniredis
```

검사는 원본 본문을 바꾸지 않지만 옆에 `.lock` 파일을 만들 수 있습니다. 정상 검사는 종료 코드 0, 손상 발견은 JSON 보고서와 종료 코드 1입니다. 서버가 자동 복구하는 EOF·UnexpectedEOF의 불완전 꼬리도 검사에서는 손상으로 보고합니다. 서버는 그 불완전 마지막 기록만 잘라냅니다. 체크섬 손상·0으로 채워진 꼬리는 자동 삭제하지 않고 시작을 거부합니다.

복구 도구는 정상 프레임 접두부만 새로운 파일로 만듭니다. 손실 동의 없이는 손상 부분을 버리지 않으며 원본·기존 출력 파일을 덮어쓰지 않습니다. 활성 서버가 잠근 파일도 거부합니다. 중간 손상 뒤에 있는 정상 기록까지 빠지므로 보고서를 확인하고 원본을 보관하세요. 임시 파일 Sync 후 하드링크로 결과를 공개하므로 출력 디렉터리 파일 시스템이 이를 지원해야 합니다. 삭제·물리 손상 데이터를 되살리거나 무손실을 보장하지 않습니다.
