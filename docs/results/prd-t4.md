# 캐시 사용·미사용 성능 비교 결과

[팀 PRD](../learning/PRD.md) T4의 기본 프로필로 측정한 결과입니다. 측정 방법과 열의 의미는 [측정 도구 문서](../benchmark.md)에 있습니다.

> 아래 수치는 **Linux 4코어 컨테이너에서 얻은 참고 측정**입니다. 제출·발표용 수치는 실제 사용하는 기기에서 같은 명령으로 다시 측정해 이 문서를 갱신하세요. 기기가 다르면 절대 수치는 달라집니다.

## 실행 설정

```bash
go run ./cmd/cachebench -scenarios warm -delays 100 -concurrency 20 \
  -warmup 10s -duration 30s -repeats 3 -aof off -products 100
```

| 조건 | 값 |
|---|---|
| 원본 지연·데이터 | 100ms, 상품 100개 균등 무작위, 시드 1, 상품 응답 약 1 KiB |
| 동시 사용자 | 20, 완료 후 다음 요청(Closed-loop) |
| 워밍업·측정·반복 | 10초·30초·3회, 반복마다 OFF와 ON의 순서를 교대 |
| 캐시 상태 | off / 웜 캐시(상품 100개를 미리 저장하고 다시 읽어 확인) |
| TTL·용량 | TTL 10분, 기본 용량. 측정 중 만료·거부 없음 |
| 확장 기능 | 영속성(AOF) 비활성, 재시도·요청 합치기·원본 우회 없음 |
| 환경 | Go 1.24.7, linux/amd64, Intel Xeon 2.10GHz 논리 코어 4개. 측정기·원본·mini-Redis가 한 기기의 루프백에서 실행 |
| 측정한 코드 | 소스 해시 `c27c7f036438` (`.go`와 `go.mod` 내용 기준). 원자료의 커밋 값은 측정 환경의 임시 저장소 것이므로 코드 식별에는 소스 해시를 사용. 해시는 테스트 파일도 포함하므로, 측정 뒤 `internal/httpapi/concurrency_test.go`의 판정만 강화한 현재 코드의 해시와는 다름(서버·측정 도구 코드는 동일) |
| 구현·스택 | Go 표준 라이브러리, 직접 구현한 체이닝 해시 테이블, 전역 Mutex |

PRD 프로필과 다른 점: 시간은 소비 앱이 아니라 측정 도구가 같은 Cache-Aside 흐름(캐시 조회 → 미적중 시 원본 조회 → 캐시 저장)을 직접 수행하며 잰 값입니다. 중간에 소비 앱의 HTTP 한 단계가 없으므로 양쪽 모두 그만큼 짧게 나옵니다.

## 결과

요약(3회 반복의 중앙값, 괄호는 최소–최대):

| 캐시 | p50 | p95 | 성공 req/s | 오류율 | 적중률 | 원본 호출 수(30초) |
|---|---|---|---|---|---|---|
| off | 100.93 ms | 101.97 ms | 198 (198–198) | 0% | - | 5,940 (요청당 1회) |
| on (웜) | 0.407 ms | 1.73 ms | 32,987 (31,089–33,938) | 0% | 100% | 0 |

p50·p95는 반복마다 구한 백분위수의 중앙값입니다. 세 반복의 표본을 모두 합쳐 다시 구한 p95는 off 101.97 ms, on 1.75 ms입니다.

실행별 결과:

| 반복 | 캐시 | 요청 수 | 성공 req/s | p50 | p95 | 원본 호출 | 실패 |
|---|---|---|---|---|---|---|---|
| 1 | off | 5,940 | 197.5 | 101.450 ms | 101.974 ms | 5,940 | 0 |
| 1 | on | 932,688 | 31,088.7 | 0.433 ms | 1.855 ms | 0 | 0 |
| 2 | on | 989,617 | 32,986.9 | 0.407 ms | 1.733 ms | 0 | 0 |
| 2 | off | 5,940 | 197.6 | 100.925 ms | 101.974 ms | 5,940 | 0 |
| 3 | off | 5,940 | 197.6 | 100.925 ms | 101.450 ms | 5,940 | 0 |
| 3 | on | 1,018,140 | 33,937.6 | 0.407 ms | 1.659 ms | 0 | 0 |

같은 반복 안에서 짝지은 비교: p50은 약 248배 짧아졌고 처리량은 약 167배(157–172배)였습니다.

## 해석

- **off는 원본 지연이 전부입니다.** 요청마다 100ms를 기다리므로 p50이 100ms를 조금 넘고, 처리량은 동시 20 × 초당 10회 = 약 200 req/s가 상한입니다. 측정값 198 req/s가 이 상한과 일치합니다.
- **on은 원본을 한 번도 부르지 않았습니다.** 측정 구간의 원본 호출 증가가 0이고 적중률이 100%입니다. 응답 시간은 mini-Redis와의 HTTP 왕복 한 번(약 0.4ms)입니다.
- **배수는 "100ms 대기를 건너뛴 효과"입니다.** 원본 지연을 100ms로 정했기 때문에 나온 숫자이며, 원본이 10ms였다면 배수도 그만큼 작아집니다. mini-Redis가 일반적으로 167배 빠르다는 뜻이 아닙니다.
- **on의 처리량 약 33,000 req/s는 서버의 최대 성능이 아닙니다.** 측정기가 4코어 중 약 2코어를 썼으므로 측정기와 서버가 CPU를 나눠 쓴 결과입니다.
- **적중률 100%인 최선의 경우입니다.** 상품 100개를 모두 미리 넣고 TTL을 길게 잡았습니다. 키가 더 많거나 만료·무효화가 잦으면 적중률이 내려가고, 미적중 요청은 off보다 캐시 왕복 두 번만큼 느립니다.
- **루프백 측정입니다.** 실제 배포에서는 캐시 왕복에 네트워크 지연이 더해져 이득이 줄어듭니다.

원본 지연 0ms, 빈 캐시, 동시 미적중, AOF 사용 시의 쓰기 비용은 PRD의 P1·별도 실험에 해당하며 `go run ./cmd/cachebench`(옵션 없이)로 측정할 수 있습니다.
